--------------------------------------------------------------------------------
Write failures are produced with the Workspace's real limits wherever possible
(mock.patch.object on workspace.MAX_FILE_BYTES and workspace.MAX_FILES, both read at
call time) plus one injected OSError for the disk-error branch. Temporary folders
only; no real user data; the network is blocked in the UI tests; generated code is
never run.

Group A - tests/test_developer_failures.py (DeveloperWriteFailureTests, 6):
  1. first file refused (MAX_FILE_BYTES=10): run FAILED at the Developer, detail
     starts "Could not write project files:" and mentions "(limit 10)", no file
     records, project_type still "calculator", nothing on disk;
  2. a later file refused (MAX_FILES=1): FAILED, "maximum of 1 files", the one
     already-written file stays on disk and in context.files with a matching
     checksum and size (pinned current behaviour: the partial project is kept);
  3. disk error on the second write (injected OSError "disk full"): detail exactly
     "Could not write project files: disk full", the loop stopped after two
     attempts, one file kept;
  4. the failed run is saved and reloaded with its partial files, project_type,
     FAILED status and final Developer event, with no load warnings;
  5. an unexpected error (RuntimeError) is not swallowed by the Developer: called
     directly it raises; through the Manager it is recorded as "RuntimeError: boom";
  6. no brief or plan (developer.py 68): FAILED "There is no approved plan to build
     from.", no updates, and no run folder created.

      writing some files, the Workspace page shows the partial file list but no error
      message: render_development shows the failure message only when no files were
      written. The run status is "failed" and the failure appears only in the progress
      strip and the activity log. The partial files also stay on disk (no cleanup).
      Pinned by test 8 and, for the disk side, test 2. The "Plan generated by
      RuleBasedPlanner" success banner also stays visible after a failed build (it
      reports the plan, not the build). Candidate fix for a later task: show the
      failure whenever a Developer FAILED event exists.

  K36 (O2) A damaged history.json looks like "No saved runs yet".
  K34 Tests depend on Streamlit internals (_page_hash, calc_hash, proto.body) only in
      the Task 008 helpers; an upgrade fails them loudly (proved for calc_hash and
      _page_hash).
