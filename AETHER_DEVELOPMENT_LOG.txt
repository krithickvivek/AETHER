1. OBJECTIVE
--------------------------------------------------------------------------------
Make sure concurrent writers and persistence failures can never silently lose
history entries (risk R1 from the architecture review), without changing the
history format, the schema, Streamlit behaviour, the Phase 2 API or the overall
architecture. No SQLite, no new dependencies, no commit or push.

--------------------------------------------------------------------------------
2. ROOT CAUSE AND RISKS FOUND (all verified in the code)
--------------------------------------------------------------------------------
  H1 No locking: save_run read the whole file, prepended an entry and rewrote it.
     Two writers (two Streamlit sessions, or Streamlit plus the future write API)
     could both start from the same old list; the later write silently dropped the
     earlier entry (a lost update).
  H2 DATA-LOSS PATH: _read_raw treated ANY OSError (for example a brief
     PermissionError on Windows) as "damaged". save_run then copied the file aside
     and wrote ONLY the new entry, so a valid history was silently replaced by one
     entry. (Reproduced end to end by the new tests against the old behaviour.)
  H3 Fixed temp name (history.tmp): concurrent writers shared one temp file; the
     replace had no retry when another program held the file; a crash left a stale
     temp file.
  H4 Invalid UTF-8 in history.json raised UnicodeDecodeError (not caught).
  H5 The damaged-copy name had one-second resolution, so a second damage within a
     second could overwrite the first copy.
  H6 RunStore._write_atomic used the fixed temp name context.json.tmp (two
     simultaneous saves of one run shared it) and had no retry.
  H7 Workspace.write_text also uses a fixed .tmp name (one writer per run; noted,
     NOT changed: out of scope).
  Constraints kept: history format and schema unchanged; legacy, newer and junk
  entries preserved byte for byte; truly corrupt files still copied aside as
  history.json.damaged-* then replaced; Streamlit still shows a damaged or
  unreadable file as an empty history (K36, by decision); _write and
  _write_atomic stay patchable by name; no *.tmp left behind; reading creates
  nothing (the API's read path is unchanged).

--------------------------------------------------------------------------------
3. IMPLEMENTATION DECISIONS
--------------------------------------------------------------------------------
Chosen: a lock file plus atomic replace plus a strict read in the update path (the
smallest reliable solution). Rejected: an in-process threading lock alone (does not
stop a second program), optimistic "re-read and compare" (the final replace cannot
be made conditional), stale-prone lock files with age-based cleanup, and SQLite
(out of scope).
  aether/fileio.py (NEW, standard library only):
    write_text_atomic  unique temp file in the same folder, flush, fsync, os.replace
                       retried on a brief PermissionError (20 tries x 50 ms); the
                       temp file is removed on ANY failure (including
                       KeyboardInterrupt) and the old file stays untouched.
    read_text_retry    read with 3 tries on a brief PermissionError.
    exclusive_lock     a thread lock plus an OS byte-range lock on a sidecar file
                       (msvcrt on Windows, fcntl elsewhere). The OS releases it when
                       the holder dies, so a crash cannot leave a stale lock.
                       Default timeout 15 s, then LockTimeout (an OSError).
  aether_ui/history.py:
    save_run and clear_history run under the lock on history.json.lock.
    _read_for_update (strict): a file that cannot be READ raises HistoryReadError
      and nothing is written; only a file that was read and is really corrupt (not
      JSON, not a list, empty, truncated, invalid UTF-8) is copied aside (a unique
      name, never overwriting an earlier copy) and replaced. If the copy fails the
      file is not replaced.
    Typed errors, all subclasses of OSError so app.py's existing "except OSError"
      toast keeps working: HistoryError > HistoryReadError, HistoryLockError,
      HistoryWriteError. Messages contain no paths. Phase 3 can map them to 503.
    Stale temp files (history.json.*.tmp) are swept under the lock (any temp file
      present while the lock is held is from a crashed writer); other files are
      never touched.
    Reading (load_history, load_history_report) takes no lock, creates nothing, and
      keeps its lenient display behaviour (K36), now with retry on a brief lock and
      invalid UTF-8 treated as damaged instead of crashing.
  aether/context.py: RunStore._write_atomic now calls write_text_atomic (same name,
    same behaviour, safer). No lock for runs (Phase 3 adds per-run locks).

6. REMAINING LIMITATIONS AND RISKS
--------------------------------------------------------------------------------
  * The lock is advisory: a program that does not use it (an older AETHER, a manual
    edit) can still write; its writes are atomic but could race with ours.
  * RunStore has atomic writes but NO lock: simultaneous saves of the same run are
    last-writer-wins. Phase 3 needs per-run locks (planned).
  * Workspace.write_text still uses a fixed .tmp name (single writer per run).
  * Streamlit still shows a damaged or unreadable history as empty (K36, by
    decision). Streamlit's "Delete all" is not wrapped in a try, so a HistoryError
    there would show an error page (the same exposure as before for a failed write).
  * A lock wait over 15 s (or a long machine suspension, K40) fails safely with
    HistoryLockError; nothing is changed.
  * Only Windows was exercised here. The POSIX (fcntl) branch is not run on this
    machine. OneDrive may briefly hold files; the retries cover that.
  * A new empty file history.json.lock appears beside the history (git-ignored).
  * Test-helper observation (pre-existing, not changed): test_history_page and
    test_workspace_page leave a TemporaryDirectory to implicit cleanup, visible only
    with -W error::ResourceWarning.
  Carried over (behaviour unchanged by owner decision): K34 tests use Streamlit
  internals; K35 a saved run whose context cannot be loaded opens silently in
  Streamlit; K36 a damaged history.json looks empty in Streamlit; K37 real-data check
  is metadata only; K38 a partial write failure shows files but no message in
  Streamlit; K39 the invalid-runs-folder error shows once in Streamlit; K40 flaky
